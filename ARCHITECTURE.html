SAP B1 AI Assistant

A beginner-friendly walkthrough of the architecture, design patterns, and technical decisions — written to prepare you for a developer interview.

01 — Overview

What Does This Project Do?

This is a chat-based AI assistant for SAP Business One (SAP B1) — an ERP (Enterprise Resource Planning) system used by businesses to manage customers, inventory, invoices, and sales orders.

Instead of navigating through dozens of screens in SAP, a user types a question like "What is the status of sales order 4242?" and the assistant fetches real data from SAP and answers in plain English using a local AI model running through Ollama.

There is also a Developer Mode where SAP B1 developers can ask the assistant to generate C# code for SAP B1 integrations — scaffolds, add-on patterns, and Service Layer snippets.
02 — Structure

The Five Projects

The solution is split into five separate C# projects. Each one has a single, clearly defined job.

Domain

SapAiAssistant.Domain

The core business rules. Pure C#, no external libraries. Defines what a ChatSession, ChatMessage, SapIntent, etc. are.

Application

SapAiAssistant.Application

Orchestrates use cases. Depends on Domain only. Declares interfaces (ports) for everything it needs but doesn't implement them.

Infrastructure

SapAiAssistant.Infrastructure

Implements those interfaces: Ollama AI client, SQLite database, SAP Service Layer HTTP calls, file-based prompt loading, vector search.

Api

SapAiAssistant.Api

Minimal REST API endpoints. The composition root — wires all layers together via Dependency Injection.

Web

SapAiAssistant.Web

Blazor Server chat UI. Talks to the API to send and receive messages. The only thing users see.

The dependency direction is strict and one-way:

Domain
←
Application
←
Infrastructure

Domain never knows about Infrastructure. This is the central rule of the entire architecture. The compiler enforces it through project references.
03 — Architecture

Clean Architecture

Popularised by Robert C. Martin ("Uncle Bob"), Clean Architecture structures code so that business rules stay isolated from external concerns like databases, HTTP, and UI frameworks.

The core idea: your application's logic should not care whether the data comes from SQLite, PostgreSQL, or a cloud database. It should not care whether the UI is Blazor, React, or a mobile app. These details are swappable without touching the business rules.
LayerProjectJob
Domain SapAiAssistant.Domain Defines what entities and value objects are. No external libraries.
Application SapAiAssistant.Application Defines what the system can do. Declares interfaces for things it needs. Talks to Domain only.
Infrastructure SapAiAssistant.Infrastructure Implements Application interfaces: Ollama, SQLite, SAP HTTP, prompt files.
API SapAiAssistant.Api Minimal API endpoints. Composition root that wires everything together.
Web SapAiAssistant.Web Blazor Server UI. Calls the API. The only user-facing surface.
04 — Design Patterns

Key Patterns Used

🔌

Dependency Inversion Principle (DIP)

This is the "D" in SOLID and the reason the architecture works. Application defines an interface (a contract); Infrastructure provides the implementation.

// Application declares what it needs:
public interface ILlmClient
{
    Task<string> GenerateAsync(string prompt, string? model = null, ...);
}

// Infrastructure provides the real implementation:
public sealed class OllamaClient : ILlmClient { ... }

// In tests, a mock is used instead (no real Ollama needed):
var llm = Substitute.For<ILlmClient>();
llm.GenerateAsync(...).Returns("fake response");

The same pattern applies to every external concern:

  • IConversationRepository implemented by SqliteConversationRepository
  • ISapAssistantGateway implemented by ServiceLayerGateway (SAP HTTP calls)
  • IIntentDetector implemented by KeywordIntentDetector
  • IPromptRenderer implemented by PromptRenderer
  • IEmbeddingClient implemented by OllamaEmbeddingClient
  • IVectorStore implemented by SqliteVectorStore
🗄️

Repository Pattern

A repository hides how data is stored and retrieved. The rest of the application only knows "give me a session by ID" — not whether that means a SQL query, a file read, or an HTTP call.

// Application layer — the contract:
public interface IConversationRepository
{
    Task<ChatSession?> GetByIdAsync(Guid sessionId, ...);
    Task<IReadOnlyList<ChatSession>> GetAllAsync(...);
    Task SaveAsync(ChatSession session, ...);
}

// Infrastructure layer — uses EF Core + SQLite:
public sealed class SqliteConversationRepository : IConversationRepository
{
    public async Task<ChatSession?> GetByIdAsync(Guid id, ...)
        => await _db.ChatSessions
            .Include(s => s.Messages)
            .FirstOrDefaultAsync(s => s.Id == id, ...);
}
Interview line: "The repository pattern decouples persistence from business logic, which lets me test the business logic in isolation and swap databases without touching Application code."
⚡

Dependency Injection (DI)

Instead of classes creating their own dependencies with new, they declare what they need in their constructor, and the framework supplies them automatically. This is called Inversion of Control.

// Registration in InfrastructureServiceRegistration.cs:
services.AddScoped<IConversationRepository, SqliteConversationRepository>();
services.AddSingleton<IIntentDetector, KeywordIntentDetector>();
services.AddScoped<IPromptRenderer, PromptRenderer>();

When an API request arrives needing a ChatService, .NET injects all its dependencies automatically.

Singleton

One instance for the entire app lifetime. Used for stateless services like KeywordIntentDetector.

Scoped

One instance per HTTP request. Used for database contexts to avoid sharing state between requests.

Transient

A new instance every time it's requested. Used for lightweight, stateless utilities.

🧱

Domain-Driven Design (DDD) Concepts

Entities — objects with a unique identity

  • ChatSession — a conversation. Has a unique Id, Mode, Title, and a list of messages.
  • ChatMessage — a single turn (user or assistant). Belongs to a ChatSession.
  • Document / DocumentChunk — an uploaded file, split into searchable pieces.

Entities are pure data containers with init-only properties — set once at creation, never mutated externally:

public sealed class ChatMessage
{
    public Guid     Id             { get; init; } = Guid.NewGuid();
    public Guid     SessionId      { get; init; }
    public MessageRole Role         { get; init; }
    public string  Content        { get; init; } = string.Empty;
    public DateTime CreatedAt      { get; init; } = DateTime.UtcNow;
    public bool    IsGroundedBySap { get; init; }
}

Value Objects — objects defined by their values

  • SapIntent — what the user is asking (e.g. BusinessPartnerLookup with CardCode = "C001").
  • ConversationContext — everything needed to assemble one LLM prompt.
  • PromptTemplate — a named, versioned prompt text loaded from a file.
05 — Request Lifecycle

How a Message Flows Through the System

This is the most important part to understand and explain. Here is the full journey when a user types "Show me customer C001":

Full request lifecycle — 10 steps
0
User types in the Blazor UI (SapAiAssistant.Web) Sends POST /api/chat/messages to the API with the user's message, mode, and optional session ID.
0
API endpoint receives the request (SapAiAssistant.Api) Calls IChatService.SendMessageAsync(request) and returns the result as JSON.
1
Load or create a ChatSession IConversationRepository.GetByIdAsync loads an existing session from SQLite, or a new ChatSession is created.
2
Add the user's message A new ChatMessage with Role = User is added to session.Messages.
3
Load conversation history IConversationMemoryStore.GetRecentAsync returns the last 10 messages so the AI has context for follow-up questions.
4
Detect intent IIntentDetector.DetectAsync → KeywordIntentDetector scans for keywords. Returns SapIntent { Kind = BusinessPartnerLookup, Parameters = { CardCode: "C001" } }.
5
Fetch SAP grounding data (if needed) ISapContextBuilder.BuildAsync → ServiceLayerGateway calls SAP B1 Service Layer REST API. Returns a formatted text block with real SAP data.
6
RAG — retrieve relevant document chunks IRagContextProvider.GetContextAsync embeds the question, searches SqliteVectorStore by cosine similarity, returns matching excerpts from uploaded documents.
7
Render the prompt IPromptRenderer.RenderAsync assembles: system prompt + mode instructions + SAP data + RAG data + history + user message into one text block.
8
Call the LLM ILlmClient.GenerateAsync → OllamaClient sends the prompt to the local Ollama server. Returns the AI's response text.
9
Save the assistant message A new ChatMessage with Role = Assistant and the AI response is added to the session.
10
Persist the session IConversationRepository.SaveAsync → SqliteConversationRepository writes everything to the SQLite database.
06 — AI Pattern

RAG — Retrieval-Augmented Generation

RAG is a technique that gives the AI access to your own documents without retraining the model. It solves the problem: "the AI doesn't know about my company's specific data."

1

Ingest

A document is uploaded, split into chunks (~500 chars each), and each chunk is converted into a vector embedding by Ollama.

2

Store

Chunks + embeddings are saved in the SQLite DocumentChunk table as float[] arrays.

3

Retrieve

The user's question is embedded. Cosine similarity finds the most relevant chunks in the database.

4

Augment

Relevant chunks are injected into the prompt so the AI can reference your documents when answering.

Cosine similarity is a mathematical measure of how "close" two vectors are — values range from 0 (completely different) to 1 (identical meaning). This is how the system finds document chunks that are relevant to the user's question.
07 — Data

Persistence: EF Core + SQLite

Entity Framework Core (EF Core) is an ORM (Object-Relational Mapper) — it lets you work with database tables as C# objects instead of writing raw SQL.

SQLite is a file-based database — no server needed, ideal for development and small deployments.

ConceptWhat it does
Migrations Versioned SQL scripts generated by EF Core. The API runs MigrateAsync() on startup to keep the schema up to date automatically.
AppDbContext The EF Core gateway to the database. Contains DbSet<ChatSession>, DbSet<ChatMessage>, DbSet<Document>, DbSet<DocumentChunk>.
IEntityTypeConfiguration EF Core configuration classes defining table structure, relationships, and cascade-delete rules — separate from entity classes.
08 — Quality

Testing Strategy

62
Unit Tests

Test one class in isolation. All external dependencies (database, AI, SAP) are replaced with mocks using NSubstitute. Tests run in milliseconds with no network needed.

var repo = Substitute.For<IConversationRepository>();
var llm  = Substitute.For<ILlmClient>();
llm.GenerateAsync(...).Returns("AI response");

var sut = new ChatService(repo, ...);
var result = await sut.SendMessageAsync(request);

result.AssistantMessage.Should().Be("AI response");
12
Integration Tests

Test the real EF Core + SQLite stack end-to-end using an in-memory SQLite database. Each test gets a fresh database. Verify that data is actually persisted and retrieved correctly.

Libraries:

  • xUnit — the test framework
  • NSubstitute — for creating mocks
  • FluentAssertions — readable assertions
09 — HTTP Pipeline

Middleware Pipeline

Every HTTP request passes through middleware in order before reaching an endpoint handler.

1
GlobalExceptionHandler

Catches any unhandled exception anywhere in the pipeline and converts it into a standardised RFC 9457 ProblemDetails JSON response. Maps exception types to HTTP status codes: ArgumentException → 400, KeyNotFoundException → 404, everything else → 500.

2
CorrelationIdMiddleware

Assigns a unique ID to each request (from the X-Correlation-Id header, or generates one). This ID is attached to all log entries for that request, so you can trace a single request across thousands of log lines in production.

3
Health Checks — /health

Reports whether Ollama, the SQLite database, and the SAP connection are all reachable. Essential for production monitoring and deployment pipelines.

10 — Trade-offs

Design Decisions & Trade-offs

Q
"Why five separate projects instead of one?"
Separation of concerns. Each project can be compiled, tested, and deployed independently. More importantly, enforcing the dependency rules at the project level means the compiler will reject any attempt to import Infrastructure code into Domain. It is a hard architectural boundary — not just a convention.
Q
"Why interfaces everywhere?"
Testability and swappability. If ChatService directly used OllamaClient, you could not test it without Ollama running, and you could not swap Ollama for another AI provider without rewriting the service. Interfaces let both scenarios work cleanly.
Q
"Why SQLite instead of a real database?"
SQLite is a deliberate v1 choice. The repository pattern means the entire database can be swapped for SQL Server or PostgreSQL by adding one new Infrastructure implementation. No Application or Domain code would change — zero impact on business logic.
Q
"Why keyword-based intent detection instead of asking the AI?"
Speed and reliability. Asking the AI to detect intent adds one extra LLM round-trip per message (~1–5 seconds). Keywords are instant. The system is designed so IIntentDetector can be swapped for an LLM-based version by changing one line in InfrastructureServiceRegistration.cs.
Q
"Why init properties instead of factory methods?"
Immutability reduces bugs. An entity whose properties cannot change after construction is easier to reason about and test. If something must change (like ChatSession.Title), it is an explicit set property, making mutations visible in code review. Entities become pure data containers with no hidden behaviour.
Q
"Why local AI (Ollama) instead of OpenAI or Azure OpenAI?"
Privacy, cost, and development simplicity. All data stays local — nothing is sent to a cloud API. The ILlmClient interface means swapping to OpenAI later is a one-class change with no impact on the rest of the system.

12 — Interview Prep

Things to Say Confidently in an Interview

  • "I applied Clean Architecture to enforce a strict dependency rule: business logic never depends on infrastructure details like the database or the AI provider."
  • "I used the Repository pattern so persistence is hidden behind an interface. Swapping SQLite for SQL Server would be a one-class change."
  • "I implemented a full RAG pipeline from scratch — document ingestion, chunking, embedding with Ollama, cosine similarity search in SQLite, and prompt injection."
  • "All external dependencies are abstracted behind interfaces, which lets me test the Application layer with mocks and without any real infrastructure running."
  • "I chose Dependency Injection to wire the system together, using ASP.NET Core's built-in container. Each class declares what it needs; the framework supplies it."
  • "I used init-only properties on entities to enforce immutability — properties are set once at creation, which eliminates a class of bugs where state changes happen in unexpected places."
  • "The intent detection layer is keyword-based in v1, but the IIntentDetector interface means I can replace it with LLM-based detection by swapping one class — the rest of the system doesn't change."
